<h2>23. WebSockets</h2>
<p class="intro">
<a href="https://en.wikipedia.org/wiki/Telnet">Telnet</a>
uses
<a href="https://en.wikipedia.org/wiki/Berkeley_sockets">Berkeley sockets</a>
to implement two-way communication between client and server.
Modern
<a href="https://en.wikipedia.org/wiki/Web_browser">web browsers</a>
have something similar:
<a href="https://en.wikipedia.org/wiki/WebSocket">WebSockets</a>.
</p>
<p>
In the previous chapter, we turned our text adventure into an online multi-player experience.
To play the game, you needed a Telnet client.
A Telnet client can still be found on most computers,
but most computer users have never used it, and are not even aware it is there.
But that is probably best for the safety of all.
Securing a Telnet connection takes effort and skill;
users are likely to give up, or worse, mess up.
</p>
<p>
Today, web browsers are the ubiquitous internet clients.
Browsing the
<a href="https://en.wikipedia.org/wiki/World_Wide_Web">world wide web</a>,
we take for granted the security measures offered by modern web browsers.
Wherever you go,
<a href="https://en.wikipedia.org/wiki/Cryptographic_protocol">encrypted connections</a>
and
<a href="https://en.wikipedia.org/wiki/Public_key_certificate">digital certificates</a>
help protect your digital identity.
</p>
<p>
So let&rsquo;s see if we can use a web browser instead of a Telnet client.
To make a web browser talk to our game server, they both need to use WebSockets.
We need to do two things:
</p>
<ol type="1">
<li>Build a <b>WebSocket client</b>.
</li>
<li>Turn our
<a href="https://en.wikipedia.org/wiki/Transmission_Control_Protocol">TCP</a>
server into a <b>WebSocket server</b>.
</li>
</ol>
<p>
The first part is easy.
A WebSocket client is basically a web page; it is the player&rsquo;s user interface.
<a href="https://en.wikipedia.org/wiki/JavaScript">JavaScript</a>
is what makes the communication happen.
<a href="https://en.wikipedia.org/wiki/MDN_Web_Docs">MDN</a>
has some excellent articles about WebSockets.
This one describes how to implement a WebSocket client in JavaScript:<br>
<a href="https://developer.mozilla.org/en-US/docs/Web/API/WebSockets_API/Writing_WebSocket_client_applications">https://developer.mozilla.org/en-US/docs/Web/API/WebSockets_API/Writing_WebSocket_client_applications</a>
</p>
<p>
Based on that knowledge, I made the following
<a href="https://en.wikipedia.org/wiki/HTML">HTML</a>
file.
When opened in a web browser, it will show a very basic
<a href="https://en.wikipedia.org/wiki/Web_page">web page</a>.
There is an input field for the player to enter commands.
The rest of the page is used to print the responses coming back from the game server.
</p>

<p>
The next step is the server.
MDN has this article that describes in full detail
how to implement the WebSocket protocol
around the Berkeley sockets we already implemented in the previous chapter.<br>
<a href="https://developer.mozilla.org/en-US/docs/Web/API/WebSockets_API/Writing_WebSocket_servers">https://developer.mozilla.org/en-US/docs/Web/API/WebSockets_API/Writing_WebSocket_servers</a>
</p>
<p>
It is doable, but still, it feels like a lot of work, and what for?
Surely, I cannot be first person on earth that wants to make a translation
between WebSocket traffic and standard Berkeley socket traffic.
I went looking for something off-the-shelf.
</p>
<p>
One possibility is a C library.
I tried
<a href="https://en.wikipedia.org/wiki/Mongoose_(web_server)">Mongoose</a>
and it worked very well.
Still, I did not like the many changes I had to make to my existing TCP server.
In this article series, each chapter should be a small step forward.
So I went looking for something less intrusive.
</p>
<p>
I settled for
<a href="https://github.com/novnc/websockify">websockify</a>.
It is a straightforward command line tool.
On a Linux server, there is a good chance
you can install (and update) it straight from a repository.
For example, here is how to install it on Ubuntu:
</p>
<table><tr>
<td class="snippet">sudo apt install websockify
</td>
</tr></table>
<p>
There are two possible ways to use websockify.
The first one is to let websockify and lilcave run side by side.
</p>
<table><tr>
<td class="snippet">./lilcave &lt;&lt;&lt;quit &amp;
websockify --web www 18812 localhost:18811
</td>
</tr></table>
<p>
This has the advantage that the same game is playable
both from Telnet clients (port 18811) and from web clients (port 18812).
If you do not care about Telnet support,
then it is also possible to let websockify act as a wrapper around lilcave:
</p>
<table><tr>
<td class="snippet">websockify --web ./www 18811 -- ../lilcave &lt;&lt;&lt;quit
</td>
</tr></table>
<p>
Open your web browser and navigate to
<a href="http://localhost:18811/">http://localhost:18811/</a>.
Enter some commands to see if it works.
</p>
<p>
The final step is to expose your game to the outside world.
</p>
<p>
How about self-hosting the game?
Traditionally, you would configure port forwarding on your internet router.
This has the disadvantage that every player needs to know your IP address.
It is the digital equivalent of inviting the whole world to your home address.
In today&rsquo;s world, it probably better to hide behind a proxy server.
A very nice option is a Cloudflare tunnel.
</p>
<p>
Do be careful, this game is written in
<a href="https://en.wikipedia.org/wiki/C_(programming_language)">C</a>,
and C is notorious for its lack of
<a href="https://en.wikipedia.org/wiki/Memory_safety">memory safety</a>.
A small bug in the program may be enough to allow a smart player
to hack your entire computer via a carefully crafted command.
</p>
<p>
Authentication is still missing in this game.
</p>
